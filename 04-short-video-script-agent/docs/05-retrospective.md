## 2. 最难的问题

### 2.1 38→28 不是“写短一点”

参考实例要求具体时长轨迹。实现上：

- 分镜秒数显式输入，`estimate_duration` 汇总；
- 长稿 10+10+9+9=38；
- 短稿 7×4=28；
- 迷你稿 4+4+3+3=14；
- 每次压缩后必须重新估算，不能只改文案不重算。

这让 Trace 能证明“观察到 38 超时 → 压缩 → 观察到 28 通过”。

### 2.2 时长与语速的冲突

压缩到 28 秒时，第 4 分镜旁白只有 12 字 / 7 秒 = 1.71 字/秒，低于 2.0 阈值，规则检查阻断。

修正：把旁白加长到 14 字，“按需开启字幕，请以实际使用为准”。这说明“短”不能牺牲可读性；时长和语速要同时满足。

### 2.3 事实追溯

P01 只有“支持字幕”。脚本中每个 claim 必须：

```text
claim.text ∈ material.facts
```

“效率提升 80%”既：

- 不在 P01 facts → `unsupported_claim`；
- 命中品牌禁用表述 → `forbidden_phrase`。

即使风格要求“夸张营销”，也不能通过。删除后重新估算/检查，最终 ready。

### 2.4 超时后的“明确失败”

目标 10 秒时，14 秒仍超。系统没有把 14 秒说成 10 秒，也没有硬砍到 10 秒：

- `duration_unmet`；
- `total=14`，`gap=4`；
- `script.ready=false`；
- pending 说明需放宽时长或减少分镜。

**反思**：Agent 的价值不只是“完成”，也包括在约束不可满足时诚实失败。

### 2.5 模型自报不可信

模型可能 finish `script_ready` 并声称 28 秒，但工具估算是 38。最终状态由工具事实决定：

- 规则 blocked → `rule_blocked`；
- 时长超 → `duration_unmet`；
- 最终 script/total 不采用 finish payload。

测试 `FalseReadyPlanner` 和 `DurationLiePlanner` 覆盖。

### 2.6 无素材场景的误命中

第一版检索 query 固定拼接“产品 素材”，导致“宠物猫粮”也命中耳机素材。去掉通用词后，无素材场景返回 `insufficient_material`。检索查询本身也会影响 Agent 是否编造。

## 3. 学习收获

1. **“时长”是可验证约束。** 必须有工具汇总，不能由模型口头保证。
2. **事实追溯要结构化。** claims + material_id + facts 比“请勿编造”更可靠。
3. **压缩要同时检查语速。** 文案变短可能让分镜不可读。
4. **规则失败应可修正。** 删除无依据 claim 后重新估算/检查，是有效的重规划。
5. **不可满足时要明确失败。** 14 秒 vs 10 秒的 gap 比虚假 ready 更有价值。
6. **检索 query 是 Agent 行为的一部分。** 泛化词会让无素材场景错误命中。
