## 2. 最难的问题

### 2.1 “建议改时段”和“擅自改硬性要求”的边界

这是业务上最容易被做错的地方。直觉方案是：发现 18:00 冲突，选 19:00，保存草稿，结束。但这会把“建议”写成“已改”。

最终方案把三个概念拆开：

1. `requested_publish_at`：任务绑定，模型参数无法修改；
2. `proposed_publish_at`：草稿建议，只在草稿中出现；
3. `confirmation.status=pending_user_confirmation`：必须由用户后续确认，工具没有“批准”入口。

保存偏离草稿时，工具强制要求 pending confirmation；`allow_time_change=false` 时连请求确认都拒绝。这样既满足参考实例“建议 19:00 并标待确认”，又没有越过“未经同意不得改变硬性要求”。

**反思**：如果只靠提示词说“不要改时间”，模型仍可能违反；必须把约束放进工具和最终状态推导。

### 2.2 幂等不只是“再查一次”

重复提交有两个坑：

1. 第二次运行时，第一次的草稿占用了 19:00，查询会把它当成“他人占用”，模型可能转而建议 20:00，创建第二份草稿；
2. 确认项也会重复创建。

解决：

- 查询时忽略**同一素材自己的草稿**；
- 草稿幂等键只包含素材 + 原要求 + 建议时段；
- 确认项按问题指纹去重；
- 保存命中幂等键时直接返回原文件，不再写。
- 测试不仅断言“返回同一 ID”，还断言 `drafts/` 文件数 = 1。

### 2.3 模型可能谎报成功

LLM 可能在保存失败后仍然 `finish(draft_saved)`。如果把模型 summary/status 直接当结果，就会虚报。

最终实现：

- `finish` 只是 `finish_claim`，不是事实；
- `_finalize` 先看草稿文件、`save_error`、审核结果；
- 有专门的 `SaveThenLiePlanner` 测试；
- 摘要由运行时生成。

这是本次最有“Agent 工程”感的点：**结果不能由模型自证**。

### 2.4 保存失败与“半个草稿”

草稿文件与索引是两次写。若文件写了、索引失败，会出现“文件存在但系统不知道”的半成功。

实现：

1. 先写临时文件，`os.replace` 原子替换；
2. 再更新 state 索引；
3. 索引失败时删除刚写的草稿文件；
4. 返回 `save_failed`，不留下可见草稿。

没有做跨进程事务；这是已知限制。

### 2.5 测试环境的 Windows 权限

本次在 DSH 的 Windows 工作区里遇到：`tempfile.mkdtemp` 创建 0o700 目录，沙箱进程无法在其下建子目录，导致大量测试失败。这不是产品逻辑问题，但会掩盖真实测试结果。

处理：测试目录改为工作区内的 `Path.mkdir()` 继承权限，并用自定义 `TestDir` 清理。记录在 `docs/04-ai-usage.md`，避免被误认为功能失败。

## 3. 学习收获

1. **Agent 的可靠性主要来自工具与状态机，不是提示词。** 规则、确认、幂等、最终状态收口都必须有代码级约束。
2. **“观察驱动”要有证据。** Trace 中每一步记录动作、参数、返回摘要和下一句决策依据；否则无法区分 ReAct 与固定流程。
3. **Mock 必须标注边界。** 离线策略能证明流程和边界，但不能证明模型判断质量；真实模型验证是独立工作。
4. **业务语义比代码更难。** “建议 19:00”“等待确认”“已保存草稿”“已发布”是四个不同状态，不能在文案里混用。
5. **失败路径要设计成产品的一部分。** 保存失败、信息不足、规则阻断、上限都应返回明确状态，而不是抛异常或假装完成。
6. **可复现性需要工程投入。** 固定数据、独立 store、一键 examples、测试结果落盘，评审才能快速核验。

## 4. 如果继续做（下一步）

### P0：提交前

- 用真实模型 Key 跑 `examples/cases/01–08`，记录模型输出与差异；
- 候选人逐文件复核，补充个人贡献/修改记录；
- 确认公开 GitHub 仓库与评审权限，推送最终 `main` 并记录 SHA；私有仓库给评审账号只读权限。

### P1：业务完整性

- 用户审批流：`pending → approved/rejected`，审批后才允许进入发布队列；
- 草稿撤销/覆盖/多方案比较；
- 冲突按素材时长计算区间重叠；
- 多日期/跨时区/节假日窗口；
- 规则热更新与版本化，草稿审核快照。

### P2：工程化

- SQLite 或事务存储 + 跨进程锁；
- 真实发布适配器（必须与草稿分离，二次确认）；
- OpenTelemetry/结构化日志；
- 真实模型评测集：正常、冲突、缺资料、规则风险、工具失败各 N 条，统计动作正确率、越权率、虚报率、平均步数；
- 红队用例：提示注入、伪造确认、要求跳过审核、要求直接发布。
