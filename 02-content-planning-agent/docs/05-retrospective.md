## 2. 最难的问题

### 2.1 “超预算”不是工具错误

最初容易把 `estimate_plan` 写成“超预算就抛错”。但这样一来，模型只看到 failure，丢失了“12 比 10 多 2”这个可用于决策的信息。

最终设计：超预算返回 `ok=true, within_budget=false, over_by=2`。模型观察后改选 8 的方案；只有**所有方案都不可行**时才 `incomplete_no_feasible_plan`，并返回最低方案与缺口。

**反思**：业务上的“不可行”是有效观察结果，不是系统异常。

### 2.2 失败后保留哪些结果

海报失败时，脚本已经成功；如果切到无海报方案，脚本应该复用。实现上：

- 成功步骤写入 `step_results`，带 `material_id`；
- 新方案 `estimate_plan` 时，只有同素材、同 step_id 的成功结果才标记 `preserved=true`；
- 海报失败本身留在 `failure_history`，不会被写成成功；
- 最终方案的 `steps` 不包含海报，但 `failure_history` 保留失败证据。

审核失败时，所有方案都有 review，无法替代，于是停止并保留 script/poster，不保存方案。

### 2.3 续跑不是“再跑一遍”

加分项的关键是 checkpoint：

- 每次工具成功/失败后写 `runs/RUN-<fingerprint>.json`；
- `--resume` 恢复成功步骤；
- 新一次 `estimate_plan` 重建 plan 时直接复用成功步骤；
- 第二次实际只执行 review/distribution，不再生成脚本/海报。

这个能力也防止重复计费/重复调用；没有 checkpoint 的“重试”只是重复劳动。

### 2.4 重复执行的两层保障

1. `get_brief` 发现同一任务指纹已有方案 → 直接 dedup，不再执行；
2. `save_plan` 仍有 request_index + idempotency key 兜底。

所以即使模型坚持跑完步骤，保存层也不会产生第二份方案。

### 2.5 模型可能虚报“已保存”

`save_plan` 失败时，模型仍可能 `finish(plan_saved)`。运行时先看 `saved_plan` 和 `save_error`，再决定最终 status；测试 `SaveThenLiePlanner` 专门覆盖。

**反思**：Agent 的“结果”不能由模型自证，必须由工具事实收口。

### 2.6 循环引用导致序列化失败

调试海报失败时遇到：

```text
ValueError: Circular reference detected
```

原因是 `error.details.plan` 指向 plan，而 plan 的 failed step 又指向 error。修复为只传 `step_id / plan_id / preserved_steps` 的扁平摘要。这个 bug 很典型：失败对象不应该反向引用完整状态树。

## 3. 学习收获

1. **预算/截止时间是约束，不是提示词建议。** 必须在工具层重新计算，保存前再校验。
2. **依赖要可执行。** `depends_on` 不是给模型看的说明，而是 `execute_step` 的拒绝条件。
3. **失败状态与成功结果要分开存。** failed step 和 successful results 是两套事实。
4. **重规划要保留上下文。** 只“换方案”不够，脚本/素材/产物能否复用决定了成本是否真的降低。
5. **续跑是状态设计。** checkpoint + 成功步骤复用，比自动重试更接近真实运营。
6. **Mock 只证明流程。** 真实模型是否会在预算和失败条件下做同样选择，需要单独评测。
